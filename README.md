# UPI Expense Tracker

A personal, local-first mobile expense tracker built with React Native + Expo.
It captures UPI payments automatically on both platforms, with a different
mechanism per OS:

- **iOS** can't read SMS, so an Apple Shortcuts automation forwards the bank
  message to a background App Intent (`ProcessSMSIntent`) that classifies it as a
  payment without opening the app and queues it for JS; only then does the
  Shortcut run a foreground intent (`OpenExpenseSMSIntent`) that brings the app up
  so JS can parse the queued text over `expo-app-intents`. A custom deep link
  (`expensetracker://add?...`) remains as a legacy/Android fallback.
- **Android** watches GPay's PIN screen with an AccessibilityService and shows a
  floating overlay to categorise the payment — the app never has to open.

Single-user, fully local (no backend, no account, no internet dependency once
installed).

---

## How it works, in one paragraph

A UPI/card debit SMS arrives from your bank → an Apple Shortcuts automation
captures the raw text (no parsing done in the Shortcut) → it runs the
`Process Incoming SMS` App Intent, a background classifier that returns whether
the message is an expense (a debit verb anchored to an amount) and, if so, queues
the text for JS → only if it is, the
Shortcut runs `Open Expense from SMS`, which opens the app so JS can drain the
queue via `expo-app-intents` → `parseAnySms()` parses the message with one shared
regex parser, and the Add Expense flow opens pre-filled with the amount,
merchant, and transaction date. Credits, balances, OTPs, statements and promos
stop at the classifier and never open the app. The bank is detected from the text
and stored as a label, not used to pick a parser. The app still accepts the legacy
`expensetracker://add?data=<url-encoded raw text>` deep link (used by the Android
capture fallback). You can also add expenses manually via the same flow, with
nothing pre-filled.

## Features

- Manual + SMS-triggered expense entry through one unified 5-slide flow
  (Amount → Category → Split → Label → Confirm)
- Category tracking: a stable manual ranking (`sort_order`) plus a dynamic
  "recently used" quick-pick (`last_used_at`)
- Expense splitting — tracks _your share_ only; full settlement between
  people is a planned future feature, not built yet
- Fully local SQLite storage — nothing leaves your device
- Activity log of every create/edit/delete action, independent of whether
  the original expense still exists
- **Android auto-capture:** reads the GPay PIN screen and prompts for category +
  split in a floating overlay (with Undo/Change) — no app switch
- Home Dashboard: month spend, spend-by-category pie chart, recent transactions
- History feed, Category management, Transaction detail (view/edit/delete) and
  Settings (learned payees + detection controls)

## Not yet built

- Multi-user sync and real "who owes who" settlement
- Budget alerts, weekly digest, yearly recap
- Dynamic Island / Live Activity as an alternate iOS trigger

The Apple Shortcut and its Message automation are written up in
[docs/ios-shortcut-setup.md](docs/ios-shortcut-setup.md), but the automation has
to be built by hand on each phone — it can't be exported or shared — so it isn't
"built" in the sense of something this repo can install for you.

## Getting started

```bash
git clone <repo-url>
cd expense-tracker
npm install
```

### iOS

```bash
npx expo prebuild --platform ios
npx expo run:ios --device --configuration Release
```

Requires a free Apple ID signed into Xcode (Xcode → Settings → Accounts →
add Apple ID) to create a Personal Team for local device signing —
no paid Apple Developer Program needed.

To wire up the SMS automation, follow
[docs/ios-shortcut-setup.md](docs/ios-shortcut-setup.md).

### Android

```bash
npx expo prebuild -p android
npx expo run:android
```

Then enable capture: in the app, **Settings → Payment detection → Enable in
accessibility settings**, and turn on **"expense-tracker payment reader"**.
Optionally add the **"Expense capture"** Quick Settings tile to pause/resume
detection. See [Android Track](#android-track).

### The capture contract

Both platforms reach the app through one shared parser, but over two channels.

**Primary (iOS): the `processSms` App Intent pair.** The Shortcut passes the raw
SMS text as the `Message Text` parameter of `Process Incoming SMS`
(`ProcessSMSIntent` in `app-intents/ProcessSMSIntent.swift`), a background
classifier (`openAppWhenRun = false`) that applies the native default-deny
debit gate (`isRejected()` / `isExpense()`) and, for an expense, calls
`AppIntentDispatcher.shared.dispatch(name: "processSms", params:)` before
returning a `Bool`. The Shortcut runs the parameterless foreground `Open Expense
from SMS` (`OpenExpenseSMSIntent`, `openAppWhenRun = true`) only when that `Bool`
is `true`, which brings the app up so JS can drain the queued dispatch.
`useAppIntentDispatcher()` (`src/hooks/useAppIntentDispatcher.ts`) receives it,
calls `parseAnySms()`, and navigates to `/add` only when `parseSucceeded` is true.
The text arrives as a typed `String`, so no URL encoding is involved.

**Fallback (Android, legacy iOS): the deep link contract.**

```
expensetracker://add?data=<percent-encoded raw SMS text>
```

- `data` is the only parameter. The bank is detected from the message text by
  `detectBankHint()` in `src/parsers/sms.ts` and stored in the `bank_source`
  column as a label.
- `data` must be percent-encoded (`encodeURIComponent` semantics). A literal `+`
  is preserved, not read as a space.
- Nothing is parsed outside `src/parsers/` — the Shortcut/intent is a dumb pipe.
  New SMS formats are a regex change, not a Shortcut change.

The Android accessibility capture uses this deep link only when the floating
overlay can't be drawn; its primary path writes straight to SQLite via
`ExpenseDb.kt`. Treat the query-string shape as stable.

## Database schema changes

`src/db/schema.ts` currently uses `CREATE TABLE IF NOT EXISTS`, which is safe for
adding new tables but does **not** apply changes to existing tables (e.g.
adding a column). Any schema change beyond a new table needs a proper
migration step (tracked via SQLite's `PRAGMA user_version`) before shipping,
to avoid silently skipping the change on devices that already have data.

## Android Track

Android can't use the iOS Shortcuts route, so capture is native:

- An **AccessibilityService** (`plugins/templates/PaymentAccessibilityService.kt`)
  watches GPay, reads the "Enter your PIN" screen (amount + payee) — with a
  fallback across all interactive windows — and fires on the Pay tap.
- A **floating overlay card** (`PaymentOverlayController.kt`) prompts for
  category + split on top of GPay, so the app never opens, then writes straight
  to the same SQLite DB via `ExpenseDb.kt`. If the card can't be drawn it falls
  back to the in-app Add flow.
- A **Quick Settings tile** pauses/resumes detection, backed by a small native
  module (`PaymentDetectionModule.kt`) that also powers the Settings screen.

The generated `android/` project is produced by `expo prebuild` from the
committed config plugin (`plugins/with-payment-accessibility-service.js`) and the
Kotlin templates, so it is gitignored — run `npx expo prebuild -p android` (or
just `npx expo run:android`) to regenerate it.

**Contribution convention:** platform capture code stays isolated — Android
under `plugins/` (+ generated `android/`), iOS under its Shortcut/App Intent flow
(`app-intents/` + `src/hooks/useAppIntentDispatcher.ts`).
`src/app/`, `src/components/`, `src/db/`, and `src/parsers/` are shared and
should only change with both platforms' agreement.
